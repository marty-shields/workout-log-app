# Dev Setup & Build
Also: [Windows setup](dev-setup-windows.md), [Linux setup](dev-setup-linux.md), [E2E tests](e2e-tests.md) and [Release](release.md) (signed APK, keystore).

## App identity
- Release: **Workout Log**, package id **`uk.martinshields.workoutlog`**. The id can't change without a reinstall, which wipes all data.
- Debug: **Workout Log (Dev)**, package id **`uk.martinshields.workoutlog.debug`**. It installs alongside the release app with its own data, so USB debugging never touches real workouts.
- Version: SemVer display version; the version code is the number of `v*` tags + 1. The release workflow sets both; local builds are `1.0.0` (1). The CI and `e2e-local.sh` Debug builds for E2E pass `-p:ApplicationDisplayVersion=1.0.0-e2e.<run id>` (`1.0.0-e2e.<epoch seconds>` locally), so the Settings version scenario checks the version of the installed package; the version code stays 1.

## Prerequisites
- .NET 11 SDK: the version in `global.json` or a later patch.
- Git and the GitHub CLI (`gh`).
- The rest depends on your OS: [Windows](dev-setup-windows.md#prerequisites) or [Linux](dev-setup-linux.md#setup).

The stories need only the .NET SDK.

## Phone setup (Android 16)
1. Settings → About phone → tap **Build number** 7 times to enable Developer options.
2. Developer options → turn on **USB debugging**, connect by USB and accept the RSA prompt. `adb devices` should list the phone.

Without USB, use wireless debugging (same Wi-Fi): turn on **Wireless debugging**, **Pair device with pairing code**, run `adb pair <ip>:<pairing port> <code>`, then `adb connect <ip>:<port>` with the port on the main Wireless debugging screen. The port changes when wireless debugging restarts.

## Development: run on the phone
Pick the phone as the target in Visual Studio or VS Code, or run `dotnet build src/WorkoutLog.App -t:Run -f net11.0-android`. Debug builds embed their assemblies, so the APK runs on its own.

## Reading the logs
- **Logcat:** `adb logcat -s WorkoutLog` (add `-d` to print and stop).
- **File:** `adb pull /sdcard/Android/data/<package id>/files/logs/`. It holds `workoutlog.log` and, past 1 MB, `workoutlog.1.log`. Without external storage it's in the app data folder; only the Debug app's can be read: `adb shell run-as uk.martinshields.workoutlog.debug cat files/logs/workoutlog.log`.

## CI
Every PR to `main` runs these; the four checks must pass before it can merge:
- **PR build** (`pr-build.yml`): the dev pipeline (`dev-pipeline.yml`) checks the E2E step bindings and the docs, builds, runs the Core and UI tests with coverage (the UI tests include source conventions in `tests/WorkoutLog.UI.Tests/Conventions`: no `DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now` or `DateTimeOffset.UtcNow` (nor their `using static` form) and no `TimeProvider.System` in `src` outside the stories site and the one registration line in `CoreServiceCollectionExtensions.cs`; SQLite used only under `src/WorkoutLog.Core/Data/`, apart from the `using SQLite;` and connection lines in `CoreServiceCollectionExtensions.cs`, no `.Execute*`, `.Query*`, `.CreateCommand` or `.FindWithQuery*` call outside `Data/` (`CoreServiceCollectionExtensions.cs` included; an unrelated `Command?.Execute(null)` fails too, so rename it), no member access on the registrar's own `connection`, no `global using` or `<Using>` item naming a SQLite type; the backup rules include only the database file `MauiProgram` names; and every E2E tag is listed in [E2E tests](e2e-tests.md#tags). They are tripwires for honest mistakes, not a proof. Type aliases (`using DT = System.DateTime;`, `using TP = System.TimeProvider;`) and reflection slip past them, and a `Data/` helper that hands out a connection lets ORM methods such as `DeleteAllAsync`, and method groups, slip outside the registrar. Run them with `dotnet test tests/WorkoutLog.UI.Tests --filter "FullyQualifiedName~Conventions"`), tests the CI scripts, lints them and the workflows, and checks `allowBackup` and `dataExtractionRules` in the Debug and Release APKs and that the arm64 Release APK holds arm64-v8a only (`check-abi.sh`, as the release does) (`dev / build-and-test`, `dev / backup-manifest`). `dev / build-and-test` also keeps the Debug APK and the E2E test output as the `e2e-build` artifact. Then the QA pipeline (`qa-pipeline.yml`) runs the E2E tests on emulators in 8 shards, each downloading `e2e-build` and restoring the E2E project instead of building, retrying failed scenarios up to 3 tries (`qa / emulator-e2e-tests`). The release workflow runs the same two pipelines, the QA pipeline after the dev pipeline.
- **PR checks** (`pr-checks.yml`): a Conventional Commit title, exactly one `semver:major`, `semver:minor` or `semver:patch` label, and dependency review (`actions/dependency-review-action`) (`pr-checks`). It can't run locally. Dependency review fails a PR that adds an npm package with a known vulnerability, in any scope including dev. NuGet is covered by `NuGetAuditMode=all`, not by dependency review, which sees no NuGet versions under central package management. Actions are covered by the GitHub-owned-only rule and Dependabot. Advisories probably don't match SHA-pinned actions, but that is unverified.
- **Drafts**: A draft PR runs only `pr-checks`. The heavy jobs (the PR build, `release-e2e.yml` and `upgrade-e2e.yml`) skip while the PR is a draft, to spare the runners. Marking it ready for review runs them. A draft cannot merge, so the missing `dev / build-and-test`, `dev / backup-manifest` and `qa / emulator-e2e-tests` checks block nothing. Do not add a stub job under a required check name, because a skipped job reports success.

- **Main build** (`main-build.yml`): every push to `main` runs the dev pipeline (`dev / build-and-test`, `dev / backup-manifest`) on the merge commit. It reports after the merge and does not stop it, so a red `main` shows up within minutes, such as two PRs that each passed alone but break together. The QA shards don't run on `main`. Runs aren't cancelled by a later push, so every commit on `main` gets its own result.

Two more run on a PR only when it changes the paths they test, and aren't required checks. The release workflow runs both on every release ([E2E tests](e2e-tests.md#other-builds)):
- **Release E2E** (`release-e2e.yml`, for `tests/WorkoutLog.E2E.Tests`, `src/WorkoutLog.Core/Export`, `src/WorkoutLog.Core/Import` and `src/WorkoutLog.Core/Data`): `build` builds the x64 Release APK once and keeps it with its debug keystore as the `release-apk` artifact. Then two jobs run on emulators. `release-e2e` checks that it starts cleanly (`release-smoke.sh`), then runs the `@release` and `@backup` scenarios on it. `release-upgrade-e2e` builds the latest `v*` tag's x64 Release APK with that keystore and runs the upgrade check from it.
- **Upgrade E2E** (`upgrade-e2e.yml`, for `tests/WorkoutLog.E2E.Tests` and `src/WorkoutLog.Core/Data`): builds the Debug APK of the latest `v*` tag (`previous-apk.sh`) and of this commit in one job, so the same debug key signs both, then runs the upgrade check (`upgrade-e2e.sh`): the tag's own E2E project saves workouts in its build, and this commit's `@upgrade` scenario checks them after installing over it ([The upgrade check](e2e-tests.md#the-upgrade-check)).

Each emulator job (the QA shards, Release E2E and Upgrade E2E) starts the emulator first, so it boots while the job builds or downloads what it tests, then ends with the `emulator-e2e` action (`.github/actions/emulator-e2e`): Appium, the emulator wait, the pinned Chromedriver, the tests under a timeout, the emulator log and the results artifact. The log and the results upload after a failure or a timeout too.

The emulator and its system image come from the Actions cache, not from Google. `.github/android-emulator.env` pins the system image, its revision, the emulator version and a cache version, and the cache key is made from them (`android-emulator-37.2.13-android-36-default-x86_64-r2-v1`). The `start-emulator` action (`.github/actions/start-emulator`) restores the two package folders, `$ANDROID_HOME/emulator` and the image's folder under `system-images`, and `emulator-start.sh` skips `sdkmanager` when both are there at the pinned versions. The jobs only restore. The **Emulator cache** workflow (`emulator-cache.yml`) saves the cache on `main`, which every PR can restore. It runs weekly, so the cache is never unused for the 7 days that evict it, and also on a push to `main` that changes the pin, and by hand. On a miss a job downloads the latest stable packages as it did before the cache (about 30 s more, and the risk of a truncated download): `emulator-sdk.sh install` makes up to 3 tries 45 s apart, deletes what a failed try unpacked, and fails when a package is missing or its license isn't accepted. The job summary shows an `Emulator cache` notice. There is no `sdkmanager --licenses`: the runner ships the one license both packages use.

Keep in step:
- NuGet restores are locked: each project commits a `packages.lock.json`, and CI (`CI` set) fails a restore that would change one (`RestoreLockedMode`). After changing a package or its version, run `dotnet restore WorkoutLog.slnx --force-evaluate` and commit the lock files. Dependabot's NuGet PRs rewrite them. Restore the App with `-p:Configuration=Release` (the Release publish needs the ReadyToRun runtime pack, which a Debug restore leaves out: NETSDK1094) but without `-r`, and publish with `-r ... --no-restore`; a restore with `-r` doesn't match the App's lock file, which lists `android-arm64` and `android-x64` (`RuntimeIdentifiers` in the App's project file). A publish with `-r` packs that one ABI only, because the project file narrows `RuntimeIdentifiers` to `RuntimeIdentifier`; without `-r` the APK holds both.
- When the SDK in `global.json` changes, set the workload set `--version` to match (`dotnet workload search version`) in the same PR, in `.github/actions/setup-maui/action.yml`. The action fails first when the pin's feature band (11.0.100.1 is 11.0.100) differs from the SDK's, so a Dependabot SDK bump fails until the pin moves too; run `.github/scripts/check-maui-pin.sh` to check locally. Every job that builds the App or the stories installs the SDK and the workload through that action. The workload set decides the WebAssembly SDK pack version the Stories lock file records, so a job without it fails the locked restore. `AnalysisLevel` is pinned to the 11.0 analysis level (`11.0-recommended`), so an SDK bump does not turn on new rules (a fix to a rule that is already on can still add a warning, which you fix the same way). Moving to a newer analysis level is a deliberate PR that fixes the code or adds a rule-off with a reason in `.editorconfig` for what fires.
- The emulator and system image are pinned in `.github/android-emulator.env`. When Google's stable channel moves past the pin, the Emulator cache workflow fails with the versions it got, and the jobs download the newer ones on every run until the pin moves. Bump `EMULATOR_VERSION` or `SYSTEM_IMAGE_REVISION` to them, with the Chromedriver pin below if the WebView changed. The PR runs the Emulator cache workflow, which fills a cache only that PR's runs can restore, and the push to `main` fills the one every PR uses. Bump `CACHE_VERSION` to rebuild the cache with the same versions.
- Chromedriver is pinned in `qa-pipeline.yml` (`CHROMEDRIVER_VERSION`, `CHROMEDRIVER_SHA256`, from [Chrome for Testing](https://googlechromelabs.github.io/chrome-for-testing/)); `chromedriver.sh` reads the pin for every E2E job and `e2e-local.sh`. When the emulator's WebView major version changes, the jobs fail: pin the matching version and its SHA-256.

On a Linux machine set up for `e2e-local.sh`, see [Keeping it current](dev-setup-linux.md#keeping-it-current).

Coverage and script tests:
- `dev / build-and-test` writes the Core and UI test results as trx. The `Test results` step (`trx-summary.py`) turns them into `::error` annotations for the failed tests and a passed, failed and skipped table in the job summary. The GitHubActions logger is not used there: with the coverage collector it failed on every result in about 1 in 60 runs, and vstest.console then stalled until the step timeout. The E2E shards use trx only too: `e2e-run.sh` reports each try the same way.
- `dev / build-and-test` collects Cobertura coverage for the Core and UI tests. The job summary lists line and branch % of `WorkoutLog.Core` (from the Core tests) and `WorkoutLog.UI` (from the UI tests) (`coverage-summary.py`) and the `coverage` artifact holds the XML (kept 14 days). The step fails when either line % is more than 1 point below `.github/coverage-baseline.tsv`, or when a line or branch rate or a baseline value is missing, unparseable, NaN or infinite. The baseline and the measured value are both rounded to 0.1 before they are compared, so the effective tolerance can be up to about 1.1 points. Refresh the baseline when coverage moves on purpose, from the XML of both runs: `python3 -I .github/scripts/coverage-summary.py --tsv WorkoutLog.Core=<Core xml> WorkoutLog.UI=<UI xml> > .github/coverage-baseline.tsv` (the `coverage` artifact of a green run has them). Locally: `dotnet test tests/WorkoutLog.Core.Tests --collect "Code Coverage;Format=cobertura" --results-directory <folder>`, then `python3 -I .github/scripts/coverage-summary.py [--baseline .github/coverage-baseline.tsv] WorkoutLog.Core=<Core xml>` (one `assembly=file` per run).
- `.editorconfig` holds the code style, and `Directory.Build.props` turns on `EnforceCodeStyleInBuild`, `AnalysisLevel=11.0-recommended` and `GenerateDocumentationFile`, so a style or analyzer warning (including naming) fails `dotnet build` like any other. `dev / build-and-test` then runs `dotnet format WorkoutLog.slnx --verify-no-changes --no-restore` for what the build does not check, such as import order, `this.` and whitespace. Run it locally without `--verify-no-changes` to fix a file. A rule turned off in `.editorconfig` carries a one-line reason.
- `.github/scripts/tests/run.sh` tests `next-version.sh` (a stub `gh` answers with canned PR JSON, in a throwaway git repo), including a release tag and commits that a force-push to main left off its history, the shard grouping in `e2e-shard-plan.sh` (the part of `e2e-shard.sh` after the `dotnet test --list-tests` call) and `failed_tests` / `filter_for` in `e2e-trx.sh` (sourced by `e2e-run.sh`), against the sample files in `.github/scripts/tests/fixtures` (the trx sample is named `.xml` because `.gitignore` excludes `*.trx`). It also tests `trx-summary.py` on small trx files. It also tests `check-filler-comments.py`, `check-docs.py` and the gate of `coverage-summary.py` on small sample files. It also tests `check-maui-pin.sh` and the run-step extractor of `lint-ci.sh` (that test needs `shellcheck`). It also tests which commit's E2E project `upgrade-seed-ref.sh` picks to save the upgrade check's workouts, in a throwaway git repo. It also tests `check-abi.sh` on zips with different native library folders. It also tests `emulator-sdk.sh` against a fake `sdkmanager`: a truncated download, a license that isn't accepted, and a stable emulator newer than the pin. It needs bash, git, jq, awk, python3 and shellcheck, and runs as a step of `dev / build-and-test`. Add a `*-test.sh` there for another script.
- `.github/scripts/lint-ci.sh` runs `shellcheck` over `.github/scripts/*.sh` and `tests/*.sh` and over the `run` steps of the composite actions in `.github/actions` (`action-run-blocks.py` writes each to a temp file, `${{ }}` replaced by a placeholder, and they are shellchecked with `-s bash`; it reads block scalars and one-line values, not every YAML form, and fails when an action has no `run` block, when its `shell:` keys and the run blocks it read differ in number (write each step as `run: |`), or when a `run` value spans several lines without being a block scalar; it reads `action.yml` and `action.yaml`), and actionlint over `.github/workflows` (it shellchecks the `run` steps too). It needs `shellcheck` on the PATH (`apt install shellcheck`; the runner image has it). It downloads actionlint at the version pinned in the script, after checking its SHA-256; to bump it, take the new version's `linux_amd64.tar.gz` digest from the release's checksums file. A real exception takes `# shellcheck disable=SCxxxx # why` above the line; `.github/scripts/.shellcheckrc` lets it follow `source`.

Doc comments and docs:
- `.github/scripts/check-filler-comments.py` fails on a `<summary>` or `<param>` in `src` or `tests` whose words are all in the name of the member, parameter or type, such as "Exercise id." on `ExerciseState.Id`. Delete the comment or say something the name doesn't. A component `[Parameter]` is skipped (the stories site shows its summary), and a real exception takes `/// <!-- filler-ok: why -->`. `Directory.Build.props` turns off CS1591 and CS1573, so a public member needs no comment. Run it with `python3 -I .github/scripts/check-filler-comments.py [paths]`; its tests are in `.github/scripts/tests`.
- `.github/scripts/check-docs.py` fails on a relative link, image or `#anchor` in a tracked `*.md` that doesn't resolve (inline, reference-style and `href`, `src` and `srcset` attributes; headings are slugged as GitHub does, and a `?query` such as the stories pages' `./?path=/story/...` isn't checked). It also fails on a `docs/images/readme/*-light.png` with no row in the README screenshots table above, or a row whose `-light.png` or `-dark.png` is missing. Run it locally with `python3 -I .github/scripts/check-docs.py` (`py -I` on Windows); its tests are in `.github/scripts/tests`.

E2E shards and step bindings:
- `e2e-shard.sh` gives each shard scenarios balanced by time, leaving out `@upgrade` and `@backup`: the longest first, each to the shard with the least time so far. It reads the median seconds of each scenario method (a Scenario Outline's rows summed, so row numbers in their names do not matter) from `.github/e2e-durations.tsv`; a row of a method missing from it counts as 15 s. The rows of a Scenario Outline stay in one shard, as do scenarios whose name starts with another scenario's name (the filter matches by name prefix). The shard log shows how many scenarios of its shard are not in the table.
- Refresh the table when scenarios are added or renamed, or their times change. Download the `e2e-results-*` artifacts of recent successful PR build runs (kept 1 day), then make the table from their trx files:
  ```
  gh run list --workflow "PR build" --status success --limit 6
  gh run download <run-id> --pattern "e2e-results-*" --dir <folder>/<run-id>   # for each run
  .github/scripts/e2e-durations.sh $(find <folder> -name "*.trx") > .github/e2e-durations.tsv
  ```
- `.github/scripts/e2e-step-check.py` matches every step in the feature files to the step definitions, as Reqnroll does when a scenario runs, and fails on a step with no definition or more than one. Run it locally with `python3 -I .github/scripts/e2e-step-check.py tests/WorkoutLog.E2E.Tests` (`py -I` on Windows).

Security scanning:
- CodeQL runs through the repo's default setup (Settings → Advanced Security: C#, Actions, JavaScript/TypeScript; no workflow file). Check it with `gh api repos/marty-shields/workout-log-app/code-scanning/default-setup`. Turn it on with `gh api -X PATCH repos/marty-shields/workout-log-app/code-scanning/default-setup -f state=configured -f query_suite=default -F languages[]=csharp -F languages[]=actions -F languages[]=javascript-typescript` and off with `-f state=not-configured`. Its results are alerts, not a required check.
- `NuGetAuditMode=all` in `Directory.Build.props` audits transitive packages too. A vulnerable package fails the build (NU1901-NU1904). Locally: `dotnet restore WorkoutLog.slnx --force-evaluate`.

Also: Dependabot opens weekly update PRs (`chore(deps): …`, `semver:patch`); every push to `main` publishes the stories to GitHub Pages (`stories-pages.yml`). Actions are GitHub-owned only, pinned by commit SHA.

## Source control
- GitHub: [marty-shields/workout-log-app](https://github.com/marty-shields/workout-log-app), public, default branch `main`.
- `main` is protected by the `Protect main` ruleset: no direct pushes, force pushes or deletion; changes go through a PR with the [CI](#ci) checks passing. PRs are opened ready for review so all CI runs; the reviewer squash-merges. Merged branches are deleted.
- Branches: `type/<issue>-slug` (e.g. `ci/123-faster-e2e-shards`, `fix/118-skip-future-workouts`); work with no issue leaves out the number (e.g. `chore/update-readme`).
